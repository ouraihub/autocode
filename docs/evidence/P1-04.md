## 契约要点

1. **6 步流程**（`commit_key_secret` / `commit_header_secret`）：
   - §5.3.1：service 自己 mint `credential_ref = wu-model-provider://credential/<uuid>`；调用方不传。
   - §5.3.2：`repo.begin_credential_put(ref)`，SQL 写 `pending_put`。
   - §5.3.3：`credentials.put(ref, secret)`。
   - §5.3.3：`credentials.get(ref)` 读回比对；不匹配或 `None` 时**先删凭据**再回 `Rejected`。
   - §5.3.4：`repo.commit_key(provider_id, expect, record)` 在 SQL 事务里 bump revision、swap metadata、drop `pending_put`、把旧 ref 塞 `pending_delete`。
   - §5.3.6：SQL commit 失败 → 删除新建的凭据 + `finish_credential_cleanup(new_ref)`，错误返回 `ServiceError::Storage`。
2. **remove**：SQL 删除 metadata + 入 `pending_delete`（§5.1 已实现），service 调用后 best-effort 调 `purge_pending_deletes` 立刻尝试删除所有 pending_delete；凭据删除失败不回退，留给下次 reconcile。
3. **reconcile_pending**（`ProviderService::reconcile_pending`，启动时调一次）：
   - 对每个 `pending_put`：如果 ref 已被 key/header 行引用，`retained += 1`；否则 `credentials.delete` + `finish_credential_cleanup`。
   - 对每个 `pending_delete`：如果 ref 又被引用（新 commit 重用），只 `finish_credential_cleanup` 掉这条日志，不删凭据；否则 `credentials.delete` + `finish_credential_cleanup`。
   - 凭据后端 `Unavailable`：保留日志，下次 boot 重试，**不删 SQL 行**。

## 已知缺口（P1-05 处理）

- 当前 `ServiceError::Storage` 是粗粒度 `anyhow::Error`，调用方无法直接区分 `NotFound/Conflict`。P1-05 会在 `ProviderService::create / update / delete_provider` 组合根里引入细粒度 `ServiceError::Conflict`。
- `tracing_stub` 占位，P1-05 接入结构化事件 `providers.credential.cleanup_failed`。
- `ProviderService` 的 Secret `clone` 是通过 `.expose().to_owned()` 实现的，用于 "write 后再 verify"；P1-05 可引入 `Secret::try_clone` 让这一步变显式。
