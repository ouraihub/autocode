## 契约要点

- **通道容量 64**：`futures::channel::mpsc::channel(64)`，满了之后调用方会排队到 broker 消费。
- **一个 Request 一次 oneshot 回复**：pump 从通道读取 `Request::Put/Get/Delete`，各自带 `oneshot::Sender<CredentialResult<...>>`。
- **前台任务**：`cx.spawn(async move |cx| while let Some(req) = receiver.next().await { ... })`，`cx.update(|cx| cx.read_credentials(url))` 在主线程持 `&mut App` 的闭包内创建 `Task`，await 时释放锁。不在 UI 回调里 block_on。
- **关闭语义**：
  - Pump task drop → receiver drop → broker 侧 `sender.send` 失败 → 调用返回 `CredentialError::Unavailable`。
  - Request 已经入队但 pump 取走前 drop → oneshot sender drop → `response.await` 得 `Err` → 转 `Unavailable`。
- **平台错误映射**（`classify_platform_error`）：
  - 字符串包含 `denied`/`cancelled`/`canceled`/`rejected`/`too large`（大小写折叠）→ `Rejected(message)`。
  - 其他 → `Backend(anyhow::Error)`，调用方允许最多一次重试，但不得假定成功。
- **不缓存明文**：broker 不在内存保留 `Secret`，`Request` 构造时移动所有权到 pump；pump 完成后 drop。
- **凭据表示**：GPUI 平台 API 要 `(url, username, password: Vec<u8>)`；broker 把 `credential_ref` 当 `url`、固定 `username = "secret"`、`Secret` bytes 当 password，每个 Key/Header 一条记录，符合 §5.3「每个 Key/Header 值单独一条」。

## 验证

便携 MSVC 工具链（`scripts\msvc\cargo-msvc.bat`）。

- `cargo check -p agent_chat` → `Finished dev` 0 error。
- `cargo test -p agent_chat --lib provider_services::` → **4/4 passed**：
  - `in_memory_vault_round_trip`：put/get/delete 回放、覆盖写、idempotent delete。
  - `in_memory_vault_forced_error_is_consumed`：forced failure 一次性生效，下次恢复正常。
  - `broker_reports_unavailable_when_task_dropped`：pump task drop 后 put/get/delete 都返回 `Unavailable`。
  - `broker_forwards_to_gpui_platform_without_panicking`：pump 存活时 put/get/delete 不 panic、不死锁；GPUI 测试平台 read 返回 `None`（§4.2 已说明这不算验收证据，保留 regression 用）。
- `cargo clippy -p agent_chat --lib --no-deps -- -D warnings` → 0 warning。

## 已知缺口

- P1-03 不做崩溃恢复逻辑：pending_put/pending_delete 的调谐在 `ProviderService` 的 `reconcile_credentials` 方法（P1-04）里编排。
- broker 当前只提供 crate-私有的 `#![allow(dead_code, unused_imports)]`；接入 P1-04 service 组合根时取消这些 allow。
- Windows / macOS / Linux 的真实平台行为用 CI 冒烟或手动验证覆盖，不在本任务内。
